# مواصفات خطوات النشر — `.dhow.yml` v1

الحالة: **v1، وعليها مدقق.** مدقق Go في `internal/pipelinespec` هو المرجع، ويستخدمه السيرفر، وجهاز التشغيل، والـ CLI (`dhow lint`). مخطط JSON Schema في `packages/spec/dhow.schema.json` للمحررات (VS Code)، واختبار يتأكد أنه مطابق للمدقق. طريقة تنفيذ السيرفر لهذه الملفات في القسم 12.

## 1. المبادئ

- **مصدر واحد للحقيقة.** خطوات النشر (pipeline) في المستودع، عند الـ commit الذي يُنشر (ADR-0008).
  - للأحداث ذات الصلاحيات (النشر، وPRs من الـ forks)، نقرأ التعريف من **الفرع الأساسي/الافتراضي**، فلا يستطيع PR أن يعيد كتابة صلاحياته.
- **الخطوات معزولة.** الخطوة إما `run:` (سكربت لـ shell *داخل البيئة المعزولة للتشغيل*) أو `uses:` (إضافة في صورة حاوية).
- **التعبيرات بلغة CEL** داخل `${{ … }}`. لها أنواع، وليست Turing-complete، ولها حدود تكلفة.
  - القيم القادمة من Git (رسالة الـ commit، والكاتب، والفرع) **بيانات**، ولا نعيد تحليلها كتعبيرات أبدًا.
- **الأسرار بالإشارة، وليست مكتوبة.** `secrets.NAME` يُحل فقط داخل نطاق البيئة الخاصة بالتشغيل.
- **قيم `env` العادية ليست سرية.** كل عضو يستطيع قراءة التشغيل يراها في الـ API والواجهة، ومنهم المشاهدون. لذلك لا تضع أبدًا رمزًا أو كلمة سر أو مفتاحًا في `env`، بل أشر إليه من `secrets`.
- **نقرأ الملف كما هو مكتوب بالضبط.** نرفض الـ anchors، والـ aliases، ومفاتيح الدمج (`<<`)، والـ tags الخاصة، لكي يكون الملف الذي تراجعه في PR هو نفسه الملف الذي يعمل.

## 2. مثال كامل

```yaml
version: 1
name: web-app

on:
  push:
    branches: [main]
  tag:
    patterns: ["v*"]
  pull_request: {}            # fork PRs: no secrets, no deploy environments
  manual:
    inputs:
      dry_run:
        type: boolean
        default: false

defaults:
  runner:
    labels: [linux, amd64]
    isolation: container        # the only level in the first release
  timeout: 20m

concurrency:
  group: ${{ project.name + "-" + git.ref }}
  cancel_in_progress: true

jobs:
  test:
    image: node:22-bookworm@sha256:61bb7a95b0f3650f3039c0fcabe07674458cf0d13afa51aade6188bab8215b07
    strategy:
      matrix:
        node: ["20", "22"]
    env:
      NODE_MAJOR: ${{ matrix.node }}
    steps:
      - name: Install
        run: npm ci --cache .npm
      - name: Test
        run: npm test -- --ci
    cache:
      key: ${{ "npm-" + matrix.node + "-" + hash_files("package-lock.json") }}
      paths: [.npm]

  build:
    needs: [test]
    image: node:22-bookworm@sha256:61bb7a95b0f3650f3039c0fcabe07674458cf0d13afa51aade6188bab8215b07
    network:
      egress: [registry.npmjs.org]      # default is deny-all
    resources:
      cpu: 2
      memory: 4Gi
    steps:
      - run: npm ci && npm run build
    artifacts:
      - name: web
        paths: [dist/, package.json, package-lock.json]

  deploy-staging:
    needs: [build]
    if: ${{ git.branch == "main" && !inputs.dry_run }}
    environment: staging
    steps:
      - uses: ghcr.io/khaymah/dhow-deploy-ssh@sha256:03fddb3b486b758f338f8999afbf04ced985d74825963dd28b92e650645e6778
        with:
          artifact: web
          target: staging-vps          # defined on the environment, credentials are env secrets
          strategy: atomic-symlink
          keep_releases: 5
          health_check_url: https://staging.example.com/healthz

  deploy-production:
    needs: [deploy-staging]
    if: ${{ git.is_tag && git.tag.startsWith("v") }}
    environment: production            # protection rules enforced server-side (see §9)
    steps:
      - uses: ghcr.io/khaymah/dhow-deploy-ssh@sha256:03fddb3b486b758f338f8999afbf04ced985d74825963dd28b92e650645e6778
        with:
          artifact: web
          target: prod-fleet
          strategy: atomic-symlink
          health_check_url: https://example.com/healthz
      - uses: ghcr.io/khaymah/dhow-notify@sha256:9b0fdebd63cc544675f3d2a9b00f975ebc573d95b42602523ea996b62c3b6a68
        with:
          channel: release-room
          message: ${{ "Released " + git.tag + " to production" }}

  migrate-db:
    needs: [deploy-production]
    image: ghcr.io/example/migrate@sha256:a8cf72fa2a047a9d6be9b105fbece66e00460b8a9fa188c439d1559100330c4d
    environment: production
    steps:
      - run: ./bin/migrate up
        env:
          DATABASE_URL: ${{ secrets.DATABASE_URL }}
```

## 3. المرجع (v1)

| المفتاح | النوع | ملاحظات |
|---|---|---|
| `version` | int | يجب أن يكون `1` |
| `name` | string | اختياري، و100 حرف بالأكثر |
| `on` | map | `push` و`pull_request` (مع `branches` و`paths`)، و`tag` (مع `patterns`)، و`manual` (مع `inputs` لها أنواع: `string` أو `boolean` أو `choice` مع `options`، و20 بالأكثر)، و`api`، و`artifact` (مع `names`: من اسم إلى 16 اسمًا، و`refs` اختيارية: يبدأ تشغيل عندما يرفع CI خارجي أحد هذه الملفات بتوكن استقبال، انظر دليل الاستقبال). يلزم حدث واحد على الأقل. نرفض `schedule` حاليًا (القسم 8) |
| فلاتر `on.*` | list | أنماط glob فيها `*` (داخل جزء واحد من المسار)، و`**` (جزء كامل، بأي عمق)، و`?` فقط، و50 نمطًا بالأكثر في كل قائمة |
| `defaults.runner` | map | `labels` (32 بالأكثر)، و`isolation` (`container` فقط في أول نسخة، القسم 8) |
| `defaults.timeout` | duration | مهلة التشغيل إذا لم يحدد التشغيل مهلة (وإلا فساعة واحدة) |
| `concurrency` | map | `group` (نص أو CEL من نوع `string`)، و`cancel_in_progress` |
| `jobs.<id>` | map | الـ id حرف صغير بعده حتى 62 من `a-z` و`0-9` و`_` و`-`. و64 تشغيلًا بالأكثر |
| `jobs.<id>.needs` | list | حواف الـ DAG. نرفض التشغيلات غير الموجودة والدوائر عند التحقق. الاعتماد على تشغيل فيه matrix ينتظر كل نسخه |
| `jobs.<id>.ingested` | list | حتى 16 اسمًا من `on.artifact.names`. كل ملف ناتج رفعه CI خارجي ننزّله ونفكه في `/workspace` قبل أول خطوة، مثل `needs`. اسم لا تذكره `on.artifact.names`، أو `ingested:` بلا `on.artifact`، هو `INGESTED_NOT_DECLARED`. التشغيل الذي لم يأت فيه أحد الأسماء يتجاوز هذا الـ job |
| `jobs.<id>.if` | CEL bool | نقيّمه قبل إدخال التشغيل في الطابور، وإذا كانت النتيجة `false` يصبح `skipped` |
| `jobs.<id>.strategy.matrix` | map | الضرب الديكارتي مع `include` و`exclude` (القسم 6)، و`strategy.max_parallel` من 1 إلى 256 |
| `jobs.<id>.image` | string | مطلوبة إذا كان في التشغيل خطوة `run:`. يجب تثبيتها بالـ digest: الصورة بالـ tag فقط تعطي تحذيرًا، والسيرفر يثبّت الـ tag على digest عند بداية التنفيذ (القسم 12.5). الاسم بلا عنوان سجل صور يُكمَل كما يفعل Docker: `node:22-bookworm@sha256:…` يعمل كـ `docker.io/library/node:22-bookworm@sha256:…`. جهاز التشغيل لا يبحث في سجلات صور أخرى أبدًا. |
| `jobs.<id>.runner` | map | نفس مفاتيح `defaults.runner`، و`labels` فيه تحل محل الافتراضية |
| `jobs.<id>.timeout` | duration | من `1s` إلى `24h`، مثل `90s` أو `20m` أو `1h30m` (الوحدات `d` و`h` و`m` و`s`، والأكبر أولًا) |
| `jobs.<id>.environment` | string | يربط قواعد الحماية والأسرار والأهداف. والتشغيل يمر على بوابة البيئة قبل أن يبدأ (§9) |
| `jobs.<id>.network.egress` | list | قائمة الأجهزة المسموحة. الفارغة تعني منع كل شيء، و64 عنصرًا بالأكثر. كل عنصر واحد من `host` أو `host:port` أو `*.domain`. (1) **الأجهزة:** حروف ASCII صغيرة، مع punycode (`xn--…`) للحروف الأخرى. نرفض عناوين IP، والأسماء المكوّنة من أرقام فقط، والأسماء من مقطع واحد (`localhost`، `*.com`). `*.domain` يطابق أي نطاق فرعي، لكن ليس `domain` نفسه. (2) **المنافذ:** بدون منفذ، يفتح العنصر 443 عبر `CONNECT` و80 لـ `http://` العادي. (3) **الوكيل:** تمر البيانات عبر وكيل جهاز التشغيل على `127.0.0.1:3128` (نضبط `HTTPS_PROXY` و`HTTP_PROXY` و`ALL_PROXY` لكل خطوة، وتغلب قيم التشغيل نفسه)، لذلك يجب أن تدعم البرامج الوكيل. يستطيع SSH وبرامج TCP الأخرى استخدام `ProxyCommand=/run/dhow/bin/connect %h %p`. (4) **غير مدعوم:** UDP، وQUIC، والبرامج التي تتجاهل الوكيل. (5) **ممنوع دائمًا:** العناوين الخاصة، وloopback، وlink-local، وعناوين metadata (ADR-0044، ADR-0057) |
| `jobs.<id>.resources` | map | `cpu` (أنوية مثل `2` أو `1.5`، أو أجزاء من الألف مثل `1500m`، من 0.1 إلى 64)، و`memory` و`disk` (بـ `Ki` أو `Mi` أو `Gi` أو `Ti`، مثل `4Gi`. الذاكرة من 64Mi إلى 64Gi، والقرص من 64Mi إلى 100Gi)، و`pids` (من 32 إلى 32768). ما لا تحدده يأخذ القيمة الافتراضية من السيرفر (معالج واحد، و2Gi ذاكرة، و4Gi قرص، و1024 عملية) |
| `jobs.<id>.env` | map | 100 متغير بالأكثر. الأسماء حروف وأرقام و`_`، والأسماء التي تبدأ بـ `DHOW_` محجوزة. كل قيمة نص أو تعبير CEL كامل من نوع `string` |
| `jobs.<id>.files` | map | ملفات أسرار لكل خطوات `run:` في التشغيل (وليس للإضافات). المفتاح اسم الملف (حروف وأرقام و`.` و`_` و`-`، حتى 128، ويبدأ بحرف أو رقم)، والقيمة `${{ secrets.NAME }}` كاملة. نكتب الملف في `$DHOW_SECRETS_DIR/<name>` بصلاحية `0400`، و20 ملفًا بالأكثر لكل تشغيل |
| `steps[].id` | string | اختياري، ولا يتكرر في التشغيل، وله نفس قواعد id التشغيل |
| `steps[].if` | CEL bool | نقيّمه قبل إدخال التشغيل في الطابور، وإذا كانت النتيجة `false` نحذف الخطوة |
| `steps[].run` | string | ينفّذه `/bin/sh -e` **داخل البيئة المعزولة**. نمرّر السكربت على stdin، ويجب أن توفّر الصورة الـ shell. 64 KiB بالأكثر، ونرفض `${{ }}` داخله (القسم 5) |
| `steps[].uses` | image ref | إضافة. يجب تثبيتها بالـ digest (`name@sha256:…`)، وإلا نرفض الملف |
| `steps[].with` | map | مدخلات الإضافة، في خطوة `uses:` فقط: 32 بالأكثر، والأسماء من `a-z` و`0-9` و`_`، والقيمة حتى 32 KiB (نص أو CEL من نوع `string`). ملف تعريف الإضافة يعلن المدخلات، وجهاز التشغيل يتحقق منها قبل أن تبدأ الإضافة ([الإضافات](#الإضافات)) |
| `steps[].env` | map | نفس قواعد `jobs.<id>.env`. القيم يمكن أن تشير إلى `secrets.*` و`vars.*` |
| `steps[].files` | map | نفس قواعد `jobs.<id>.files`، لهذه الخطوة فقط. وخطوة `uses:` لا تأخذ `files:`، فهي تأخذ أسرارها من `with:` (`SECRET_FILES_ON_PLUGIN`) |
| `steps[].timeout` | duration | لا تزيد عن مهلة التشغيل |
| `artifacts` | list | 16 بالأكثر لكل تشغيل. `name` (حروف وأرقام و`.` و`_` و`-`، حتى 64، ولا يتكرر في خطوات النشر كلها: في تشغيل فيه matrix، اجمع نصًا وقيم `matrix.*` بـ `+`، مثل `${{ "web-" + matrix.os }}`)، و`paths` (من 1 إلى 32، نسبة إلى مساحة العمل، بدون `..` أو `~` أو `/` في البداية)، و`retention` (من `1d` إلى `30d`، والافتراضي 30 يومًا) |
| `cache` | map | `key` (نص أو CEL من نوع `string`، ويمكن أن يستدعي `hash_files()`)، و`paths` (نفس قواعد مسارات الملفات الناتجة). محدود لكل مشروع وفرع. وتنفيذات الـ forks لا تكتب فيه أبدًا، ولا تقرأ منه إلا إذا سمح المشروع (القسم 12.4) |

**سياق CEL.** هذه المتغيرات متاحة:
- `git.{sha, ref, branch, tag, is_tag, message, author, event}` و`git.pr.{number, base_ref, head_ref, is_fork}`
- `project.{id, name}` و`env.*` (قيم `env` الخاصة بالتشغيل، في حقول الخطوات ومفتاح الـ cache)
- `vars.*` (غير سرية: متغيّرات المؤسسة ثم المشروع، والأقرب يكسب، وأسماؤها من غير فرق بين الحروف الكبيرة والصغيرة. وتنفيذات الـ forks تأخذها فارغة)
- `inputs.*` (مدخلات `manual` المعلنة، بأنواعها)
- `secrets.*` (كقيمة كاملة في `env`/`with` فقط، ولا يمكن أن تظهر في `if` أبدًا)
- `matrix.*` و`needs.<job>.outputs.*` (للتشغيلات المذكورة في `needs` فقط، وبشرط ألا يكون في id التشغيل `-`)

وهذه الدوال متاحة: `hash_files()` (في مفتاح الـ cache فقط، ويقيّمها جهاز التشغيل داخل مساحة العمل)، و`startsWith()`، و`endsWith()`، و`contains()`، و`size()`، وباقي المكتبة الأساسية لـ CEL، ما عدا `matches()` (لأن التعبيرات النمطية لا يمكن إيقافها في منتصفها) ودوال الوقت (`timestamp()` و`duration()` ودوال `get…()`، لأنها قد تقرأ ملفات المناطق الزمنية).

للقيم في السياق حدود، والتقييم بقيمة أكبر يفشل: `git.message` حتى 64 KiB، وباقي قيم `git.*` و`project.*` حتى 1 KiB، و`vars.*` و`inputs.*` حتى 4 KiB (و256 متغيرًا)، و`env.*` حتى 32 KiB (و100 متغير)، وكل output من `needs` حتى 1 KiB (و64 output). واسم `env` الذي يحمل سرًا لا يظهر أبدًا في `env.*`.

### سحب الكود

كل تشغيل في خط نشر يبدأ بسحب commit التشغيل إلى `/workspace`. لا تكتب شيئًا لذلك في `.dhow.yml`.

- **أين يعمل:** في بيئة معزولة خاصة، من صورة `dhow-git` التي يثبّتها جهاز التشغيل بالـ digest. هذه البيئة تصل إلى خادم المستودع فقط، مهما كانت قائمة `network.egress` في التشغيل.
- **ماذا يجلب:** الـ ref الخاص بالتشغيل بـ `--depth=1`، ثم commit التشغيل بالضبط. إذا تحرك الفرع، يجلب جهاز التشغيل جزءًا أكبر من تاريخ الفرع على خطوات (64 ثم 1024 ثم 65536 commit)، الـ commits وحدها بدون ملفاتها ولمدة دقيقتين بالأكثر، ويتأكد أن الـ commit فيه (`git merge-base --is-ancestor`). والـ commit الذي ليس في تاريخ الـ ref (الفرع أُعيد كتابته أو حُذف، أو الـ commit موجود في فرع آخر فقط) لا نجلبه برقمه أبدًا: يفشل التشغيل بـ `CHECKOUT_REF_MOVED`. وبعدها نجلب ملفات commit التشغيل وحده، فأمر `git` منك يحتاج ملفات commit أقدم عليه أن يجلبها. الـ submodules وملفات LFS والـ hooks والتحويلات مقفولة، ويمكن لخطوة منك أن تجلبها باتصالاتها الخارجية.
- **بيانات الدخول** (مفتاح deploy key عبر SSH، أو رمز قصير العمر عبر HTTPS) ملف في بيئة السحب فقط. لا تحصل عليها خطواتك ولا إضافاتك أبدًا، لا في البيئة ولا في ملف ولا في `/proc`. وعبر SSH لا نقبل إلا مفتاح الخادم الذي أكّده المدير للمستودع، وأي مفتاح آخر يفشّل التشغيل بـ `HOST_KEY_MISMATCH`.
- **أجهزة التشغيل القديمة:** التشغيل الذي فيه سحب للكود يذهب فقط إلى جهاز تشغيل أعلن ميزة `checkout` عند دخوله. وحتى يتصل جهاز تشغيل مثل هذا، ينتظر التشغيل في الطابور.

### الإضافات

خطوة `uses:` تشغّل صورة حاوية في بيئة معزولة خاصة، على نفس `/workspace` ومع قائمة `network.egress` الخاصة بالتشغيل. لا تستطيع الإضافة توسيع هذه القائمة. ولا تحتاج الصورة إلى shell.

تعلن الصورة مدخلاتها ومخرجاتها وأمر تشغيلها في الـ label `io.dhow.plugin.manifest`:

```json
{"Version": 1, "Entrypoint": ["/usr/local/bin/notify", "--quiet"],
 "Inputs": {"channel": {"Required": true}, "message": {"Default": "done"}}, "Outputs": ["url"]}
```

- `Entrypoint` يبدأ بمسار مطلق، ويعمل كما هو بدون shell (32 وسيطًا بالأكثر).
- كل مفتاح في `with:` يجب أن يكون في `Inputs`، وكل مدخل عليه `Required` يجب أن تضبطه أو أن تكون له قيمة `Default`. وإلا تفشل الخطوة بـ `PLUGIN_INPUT_INVALID` قبل أن تبدأ الإضافة. والصورة التي ليس فيها label صحيح تفشل بـ `PLUGIN_MANIFEST_INVALID`.
- كل مدخل يصل إلى الإضافة كمتغير بيئة `DHOW_INPUT_<NAME>`، والاسم بحروف كبيرة (`DHOW_INPUT_CHANNEL`). ولا يقرأ أي shell القيمة أبدًا. المدخل الذي عليه `"Kind": "artifact"` (يجب أن يكون `Required` وبلا `Default`) يسمّي ملفًا ناتجًا من التشغيل: يتأكد جهاز التشغيل من الـ digest ويعطي الإضافة الأرشيف غير مفكوك كملف، مع `DHOW_INPUT_<NAME>_FILE` لمساره و`DHOW_INPUT_<NAME>_DIGEST`. و`"Mutating": true` في الـ manifest تجعل جهاز التشغيل يبدأ الخطوة على أنها تغيّر شيئًا، فلا يعاد التشغيل بعد بدايتها.
- **الإضافة تحصل فقط على ما نعطيه لها:** مدخلاتها، و`DHOW_OUTPUT`، ومتغيرات الـ proxy لاتصالات التشغيل الخارجية، و`env` الخاص بخطوتها، والأسرار المعطاة لهذه الخطوة. السر في `with:` (`token: ${{ secrets.CHAT_TOKEN }}`) يصل كـ `DHOW_INPUT_TOKEN` وفي هذه الخطوة فقط. والخطوة التي يتخطاها شرط `if:` تأخذ أسرارها معها، ولا تحصل أي خطوة أبدًا على سر معلَن على خطوة أخرى: يتأكد السيرفر من ذلك قبل وضع التشغيل في الطابور، وإلا يفشل التشغيل بـ `JOB_SPEC_INVALID`. أما `env` الخاص بالتشغيل، والأسرار المعطاة للتشغيل كله، و`DHOW_FENCING_TOKEN` و`DHOW_JOB_ID` و`DHOW_ATTEMPT_ID` و`DHOW_STEP_INDEX`، فلا تصل أبدًا إلى إضافة.

### إضافات النشر على هدف

الخطوة `uses:` التي فيها `with.target` تنشر على [هدف](guides/environments.md#أهداف-النشر) معرَّف في بيئة الـ job. القواعد التالية يفحصها السيرفر حين يضع الـ job في الطابور، وإذا خالفها الـ job يفشل بالسبب المذكور ولا يُفتح أي سر:

- الـ job يكتب `environment:`، وإلا `TARGET_REQUIRES_ENVIRONMENT`.
- اسم الهدف نص ثابت في الملف، لا تعبير ولا سر، وإلا `TARGET_NOT_LITERAL`.
- الهدف موجود في بيئة الـ job، وإلا `TARGET_NOT_FOUND`.
- إضافات النشر الرسمية وحدها تستلم هدفًا، بالاسم الكامل بالضبط، أو صور يسمح بها الهدف في `AllowedImages`، وإلا `TARGET_PLUGIN_NOT_ALLOWED`. وتُكتب الصورة ببصمتها `@sha256:`، وإلا `TARGET_PLUGIN_NOT_PINNED`.
- لا تذكر أي خطوة السر الذي يحمل مفتاح هدف في البيئة، لا خطوة `run:` ولا أي إضافة، وإلا `TARGET_KEY_NOT_REFERENCEABLE`. المفتاح يصل لخطوة النشر وحدها، ويفحص السيرفر هذا عند البدء أيضًا.
- التشغيل القادم من fork لا ينشر على هدف أبدًا، ويفشل بـ `FORK_PR_NO_ENVIRONMENT`.
- لكل سيرفر في الهدف مفتاح مثبّت، وإلا `TARGET_HOST_KEY_UNCONFIRMED` مع عناوين السيرفرات.
- سر مفتاح الدخول موجود في البيئة، وإلا `TARGET_KEY_NOT_FOUND`.
- `with.artifact` يذكر ملفًا ناتجًا يرفعه تشغيل في `needs`، وإلا `TARGET_ARTIFACT_REQUIRED`.
- `with.health_check_url` عنوان `http` أو `https` بلا اسم مستخدم، ويمكن أن يحمل `{host}` مكان اسم السيرفر كاملًا ليُفحص كل سيرفر على عنوانه، وإلا `HEALTH_URL_INVALID`. وسيرفر الفحص هو `{host}` أو سيرفر من سيرفرات الهدف نفسها، وإلا `HEALTH_URL_NOT_ALLOWED`. وإذا فتح المدير `AllowExtraDeployEgress` يسمح السيرفر باسم عام آخر، ولا يسمح أبدًا بعنوان محلي أو خاص أو عنوان خدمة السحابة (metadata).
- فحص الصحة لا يتجاوز 10 دقائق لكل سيرفر (`HEALTH_BUDGET_EXCEEDED`)، والنشر على دفعات لا يتجاوز 60 دقيقة (`ROLLING_BUDGET_EXCEEDED`).
- الـ job الذي ينشر يصل إلى سيرفرات هدفه وإلى عنوان فحص الصحة فقط. يحسب السيرفر هذه النقاط من الهدف، فلا يستطيع الملف تغييرها. وكل `network.egress` آخر في الـ job مرفوض بـ `TARGET_JOB_EGRESS_NOT_ALLOWED`، إلا إذا فتح المدير `AllowExtraDeployEgress` في البيئة.

مدخلات إضافة SSH الرسمية وما تفعله على السيرفر موصوفة في [النشر على سيرفر بـ SSH](guides/deploy-ssh.md).

يضع السيرفر خطوة النشر علامة «تغيّر شيئًا» (`mutating`)، فلا يعاد الـ job تلقائيًا بعد أن تبدأ. ويُسلَّم مفتاح الدخول كملف لهذه الخطوة وحدها، ولا تراه خطوة `run:` ولا إضافة أخرى.

عند بدء الـ job على الـ runner يفحص السيرفر مرة أخرى قبل أن يفتح المفتاح: إذا تغيّر الهدف أو سيرفراته أو ترتيبها أو مفتاح أحدها بعد وضع الـ job في الطابور، يفشل بـ `TARGET_CHANGED`. وإذا حُذف سر المفتاح يفشل بـ `TARGET_KEY_NOT_FOUND`. الـ runner الذي لا يعلن الميزة `deploy_targets` لا يستلم هذا الـ job.

### مخرجات الخطوات

كل خطوة، `run:` أو `uses:`، تحصل على المتغير `DHOW_OUTPUT`، وهو ملف تكتب فيه أسطر `key=value`. والتشغيلات التي تذكر هذا التشغيل في `needs` تقرأ القيم كـ `needs.<job>.outputs.<key>`.

- المفاتيح حروف وأرقام و`_` ولا تبدأ برقم، والقيمة حتى 1 KiB في سطر واحد. يحتفظ التشغيل بـ 64 output بالأكثر، والخطوة التالية تكتب فوق مفتاح الخطوة السابقة.
- لا تكتب الإضافة إلا المفاتيح الموجودة في `Outputs` في ملف تعريفها.
- السطر الذي يخالف هذه القواعد يفشّل الخطوة. ونحتفظ بالمخرجات فقط إذا نجح التشغيل، وأيضًا إذا أعيد تشغيل جهاز التشغيل قبل أن يستلم السيرفر النتيجة.
- **من يراها:** الـ output، وكل قيمة أخرى صنعها تعبير (`env: VERSION: ${{ needs.build.outputs.version }}`، أو قيمة من `git.*`)، يصل إلى خطوات التشغيل كما هو، لكن تفاصيل التشغيل في الـ API والواجهة تعرض `[REDACTED]` مكانه، لكل الأدوار.
- **الإخفاء:** تفحص أداة الإخفاء كل قيمة، وتفحص أيضًا القيم مجموعة معًا (كل سلسلة مفاتيح متتالية بترتيب الأسماء، وكل زوج بأي ترتيب). السر داخل قيمة يصبح `***`، والسر الذي يظهر فقط عند جمع القيم نحذف كل المفاتيح التي يمر بها. والسر الأقصر من 4 حروف لا يمكن إخفاؤه في أي مكان (ويذكر سجل التشغيل ذلك)، لذلك قد يخرج في output.

### الملفات الناتجة والذاكرة المؤقتة

الملف الناتج (artifact) يحفظ ملفات تشغيل واحد للتشغيلات التي تحتاجه، وللتحميل. والذاكرة المؤقتة (cache) تحفظ ملفات، مثل مجلد مدير الحزم، من تنفيذ إلى التنفيذ التالي.

- **الأرشيف:** يجمع جهاز التشغيل كل ملف ناتج والذاكرة المؤقتة في tar.gz يكون هو نفسه للملفات نفسها: الملفات مرتبة، والأوقات صفر، ومن غير مالك، والصلاحيات `0644` أو `0755`. نحتفظ بالروابط الرمزية التي تبقى داخل مساحة العمل، والرابط الذي يخرج منها أو الجهاز أو الـ FIFO أو الـ socket يفشّل التشغيل بـ `ARTIFACT_UNSAFE`. واسم الأرشيف هو الـ SHA-256 الخاص به، فالملفات نفسها تعطي البصمة نفسها.
- **أين يعمل:** الجمع والفك و`hash_files()` تعمل في sandbox خاص بها، من صورة سحب الكود في جهاز التشغيل، من غير شبكة، على مساحة عمل التشغيل وداخل user namespace الخاص به. جهاز التشغيل نفسه لا يقرأ مساحة العمل ولا يكتب فيها أبدًا.
- **الرفع:** بعد نجاح كل الخطوات، نجمع كل ملف ناتج ونرفعه. المسار غير الموجود يفشّل التشغيل (`ARTIFACT_UPLOAD_FAILED`)، والأرشيف الأكبر من `DHOW_ARTIFACT_MAX_BYTES` يتوقف في منتصفه (`ARTIFACT_TOO_LARGE`). والتشغيل الفاشل لا يرفع شيئًا.
- **`needs`:** قبل أول خطوة، ننزّل الملفات الناتجة للتشغيلات المذكورة في `needs`، ونتأكد من الـ SHA-256 على جهاز التشغيل، وبعدها فقط نفكّها في `/workspace`. البصمة التي لا تطابق تفشّل التشغيل بـ `ARTIFACT_DOWNLOAD_FAILED` ولا نفك شيئًا. ويرفض الفك `..` والمسارات المطلقة والروابط التي تخرج من مساحة العمل والأجهزة والـ FIFO والروابط الصلبة لملفات خارج الأرشيف (`ARTIFACT_UNSAFE`).
- **الاحتفاظ:** نحتفظ بالملفات الناتجة مدة `retention` (من يوم إلى 30 يومًا، ولا تزيد أبدًا على `DHOW_ARTIFACT_RETENTION_DAYS`)، ثم نحذفها. والاستثناء الوحيد ملف إصدار نجح نشره على هدف وما زال من آخر إصدارات الهدف المحفوظة: نبقيه للرجوع إليه حتى 90 يومًا بعد انتهاء مدته، ويُحسب من حصة المؤسسة. ويستطيع دور Developer وما فوقه عرض ملفات التنفيذ وتحميلها (`GET .../runs/{runId}/artifacts` و`GET .../artifacts/{artifactId}/download`).
- **مفتاح الذاكرة المؤقتة:** يقيّم السيرفر `cache.key`، ويترك كل استدعاء لـ `hash_files()` لجهاز التشغيل، فيملؤه في بداية التشغيل بـ SHA-256 للملفات المطابقة (مرتبة بالمسار، ولكل ملف SHA-256 الخاص به). تأخذ `hash_files()` أنماط glob (`*` و`**` و`?`) نسبية لمساحة العمل، ويستخدم المفتاح نتيجتها كنص فقط، فنرفض `size(hash_files(...))` أو أي شرط عليها. والمفتاح النهائي من 1 إلى 512 حرفًا.
- **نطاق الذاكرة المؤقتة:** النطاق تابع للمستودع المربوط، فربط المشروع بمستودع آخر يبدأ بذاكرة مؤقتة فارغة. الـ push أو التنفيذ اليدوي لفرع يكتب في نطاق هذا الفرع، والـ tag في نطاقه، وطلب الدمج من المستودع نفسه في نطاق طلب الدمج. والبحث يجرّب نطاق التنفيذ أولًا، ثم الفرع الافتراضي. وطلب الدمج من fork لا يكتب أبدًا، ولا يقرأ شيئًا إلا إذا سمح المشروع بالفرع الافتراضي (القسم 12.4). ولا يستطيع أي طلب دمج أن يكتب في نطاق `main`. والتنفيذ اليدوي أو من الـ API على commit ليس آخر ما وصل للفرع يقرأ الذاكرة المؤقتة فقط، فآخر commit في الفرع وحده يكتب فيها.
- **الحفظ:** نحفظ الذاكرة المؤقتة فقط إذا نجح التشغيل ولم نجد المفتاح في البداية. ولا نستبدل مفتاحًا موجودًا أبدًا. وعندما تتجاوز مدخلات المشروع `DHOW_CACHE_MAX_BYTES_PER_PROJECT`، نحذف أولًا الأقدم استخدامًا من النطاقات الأخرى، ولا نحذف أبدًا مدخلات الفرع الافتراضي لنفسح مكانًا لفرع آخر أو tag أو طلب دمج، والمدخل الذي لا يكفيه المكان بعد ذلك لا نحتفظ به. والذاكرة المؤقتة التي لا نستطيع قراءتها أو حفظها تظهر كتحذير في سجل التشغيل، ولا تفشّل التشغيل.
- **رفع واحد لكل ملف:** يرفع التشغيل كل ملف ناتج معلن وذاكرته المؤقتة مرة واحدة. وتشترك الملفات الناتجة للمؤسسة في `DHOW_ARTIFACT_MAX_BYTES_PER_ORG` (وبعده `ARTIFACT_QUOTA_EXCEEDED`). والملفات الناتجة من تنفيذات الـ forks في المشروع الواحد تأخذ معًا عُشره بالأكثر، فلا تستطيع الـ forks، حتى مع سياسة `automatic`، أن تملأ مساحة تنفيذات المشروع نفسه.
- **`ingested`:** الملف الناتج الذي يرفعه CI خارجي نحتفظ به مثل أي ملف آخر مدة `DHOW_ARTIFACT_RETENTION_DAYS`. يقرأ التشغيل ملف الـ pipeline من رأس الفرع الافتراضي وليس من الـ commit الذي أعلنه الرافع، ويأخذ الـ job الـ digest نفسه الذي رُفع. والـ `Sha` والمنشأ (اسم الـ CI ورابط التشغيل والفاعل) يعلنها الرافع ولا نتحقق منها.
- **الـ forks:** الملفات الناتجة من تنفيذ طلب دمج من fork نعلّمها `Untrusted`، ولا تصل أبدًا إلى نشر.
- **الأسرار:** قبل الرفع يبحث جهاز التشغيل في كل ملف عن قيم أسرار التشغيل بكل صيغها (القيمة نفسها وbase64 وغيرها). الملف الناتج الذي فيه قيمة سر يفشّل التشغيل بـ `ARTIFACT_CONTAINS_SECRET`، والسجل يذكر اسم الملف فقط. والذاكرة المؤقتة التي فيها قيمة سر لا نحفظها، ويظهر تحذير في السجل. الفحص على الملفات كما هي، فالملف المضغوط أو المشفّر داخل الأرشيف لا يغطيه. والذاكرة المؤقتة التي كتبها تشغيل وصله سر لا تصل أبدًا إلى fork.

## 4. التعبيرات

- **أين:** `if` (للتشغيل والخطوة)، و`concurrency.group`، و`cache.key`، وقيم `env` و`with`، و`name` للملف الناتج (وفيه نص وقيم `matrix.*` مجموعة بـ `+` فقط، لكي نعرف الأسماء بدون تشغيل أي شيء). كل حقل آخر نص عادي، و`${{` فيه خطأ.
- **القيمة كاملة:** التعبير هو القيمة كلها: `${{ "v" + git.tag }}`، وليس `v${{ git.tag }}`. اجمع النصوص بـ `+` داخل CEL.
- **`if`** يمكن كتابته مع `${{ }}` أو بدونه.
- **نتحقق من الأنواع عند التحقق من الملف، وليس عند التشغيل.** يجب أن يكون `if` من نوع `bool`، وكل مكان آخر من نوع `string`، وأي اسم غير متاح في هذا المكان خطأ. لذلك نرفض `if: ${{ git.branch }}` قبل أن يعمل أي شيء.
- **الأسرار:** `${{ secrets.NAME }}` مسموح فقط كقيمة كاملة في `env` أو `with`. القيمة لا تمر عبر CEL أبدًا: يستلمها جهاز التشغيل كإشارة إلى سر. استخدام `secrets` في `if`، أو في `concurrency`، أو في `cache`، أو داخل تعبير أكبر، خطأ.
- **الحدود:** 2 KiB لكل تعبير، و1,024 تعبيرًا بالأكثر في خطوات النشر كلها. نحسب أعلى تكلفة ممكنة لكل تعبير من حدود القيم السابقة عند التحقق من الملف، ونرفض التعبير الذي قد تكون تكلفته كبيرة (`EXPRESSION_TOO_EXPENSIVE`)، وكذلك الملف الذي قد تكون تكلفة تعبيراته معًا كبيرة (`EXPRESSION_BUDGET_EXCEEDED`). وعند التشغيل، يتوقف التقييم أيضًا عند نفس حد التكلفة وبعد 10 ms. لا توجد دالة تقرأ ملفات أو تتصل بالشبكة على السيرفر.

## 5. سكربت `run:`

لا نسمح أبدًا بـ `${{ }}` داخل `run:`. لو سمحنا به، يمكن أن تصبح قيمة من Git، مثل اسم فرع أو رسالة commit، جزءًا من السكربت (وهذا هو حقن الأوامر المعروف في GitHub Actions). مرّر القيمة عبر `env` واقرأها كمتغير في الـ shell:

```yaml
version: 1
on:
  push: {}
jobs:
  greet:
    image: alpine:3.22@sha256:61bb7a95b0f3650f3039c0fcabe07674458cf0d13afa51aade6188bab8215b07
    steps:
      - run: printf 'building %s\n' "$BRANCH"
        env:
          BRANCH: ${{ git.branch }}
```

- يعمل السكربت بـ `/bin/sh -e` ونمرّره على stdin، لذلك يتوقف عند أول أمر يفشل.
- حجم السكربت 64 KiB بالأكثر، وبدون بايتات NUL.

## 6. الـ matrix

- كل مفتاح تحت `matrix` (ما عدا `include` و`exclude`) فيه قائمة قيمه: نصوص أو أرقام أو قيم منطقية، 128 حرفًا بالأكثر. المفتاح حرف أو `_` بعده حروف وأرقام و`_`، و16 مفتاحًا بالأكثر.
- التشغيلات هي الضرب الديكارتي للمفاتيح، مرتبة حسب المفتاح. واسم كل تشغيل مثل `build (node=20, os=debian)`.
- **`exclude`** يحذف كل تركيبة تطابق كل أزواج عنصر منه. العنصر يستخدم مفاتيح الـ matrix فقط.
- **`include`** يضيف تركيبة جديدة لكل عنصر (وعلى عكس GitHub Actions، لا يعدّل التركيبات الموجودة أبدًا). العنصر يحدد كل مفاتيح الـ matrix، لكي يكون لكل تشغيل نفس قيم `matrix.*`. يمكن أن يكون في الـ matrix `include` فقط، وعندها تستخدم كل العناصر نفس المفاتيح.
- **الحدود:** 256 تشغيلًا بالأكثر لكل matrix، و256 تشغيلًا في خطوات النشر كلها بعد التوسيع. الـ matrix التي لا تبقى فيها أي تركيبة خطأ، وكذلك تركيبتان لهما نفس الاسم.
- التوسيع ثابت: نفس الملف يعطي دائمًا نفس التشغيلات بنفس الترتيب، ونفس الـ digest لمواصفات كل تشغيل.

## 8. غير مدعوم بعد

- **الحدث `schedule`** يأتي بعد أول نسخة. نرفضه بـ `TRIGGER_NOT_SUPPORTED_YET`، ولا نتجاهله.
- **`isolation: gvisor`** نرفضه بـ `ISOLATION_NOT_SUPPORTED_YET` حتى يعود gVisor بعد أول نسخة.
- **`id_token:`** (توكن OIDC للخدمات السحابية) يأتي بعد أول نسخة، ونرفضه بـ `ID_TOKEN_NOT_SUPPORTED_YET`.
- **`services:`** (حاويات تعمل طوال التشغيل) والمحرر المرئي يأتيان بعد أول نسخة.

## 9. حماية البيئات (في السيرفر، وليست في YAML)

تُضبط قواعد الحماية على البيئة من الواجهة أو الـ API، لذلك **لا يستطيع commit أن يضعفها**. القاعدة يمكن أن تحدد:
- الفروع أو الوسوم المسموحة؛
- المراجعين المطلوبين (العدد والفرق)، مع خيار منع الشخص من الموافقة على طلبه؛
- مؤقت انتظار ونوافذ نشر، ومنها فترات التجميد؛
- مستوى العزل المطلوب، واشتراط صور مثبّتة بالـ digest وإضافات موثّقة؛
- تجاوز للمدير، يُسجَّل في سجل الأحداث.

قبل أن يبدأ التشغيل الذي فيه `environment:`، يمر على **بوابة البيئة**: البيئة موجودة، والفرع أو الوسم مسموح، والصور والإضافات تطابق القواعد، والأسرار موجودة، ثم الإيقاف والمراجعون والمؤقت، وتنفيذ واحد في البيئة في كل مرة. التفاصيل في [دليل البيئات](guides/environments.md#البوابة).

## 10. المحرر المرئي

بعد أول نسخة، تقدّم الواجهة محررًا مرئيًا لخطوات النشر (رسم للتشغيلات مع نماذج للخطوات)، موجّهًا للمستخدمين الجدد. يعمل هكذا:
- يقرأ `.dhow.yml` الحالي في الفرع الافتراضي.
- يعدّل نموذجًا له أنواع، ويتحقق منه مباشرة بمخطط JSON Schema نفسه.
- **يكتب YAML ويفتح pull request** عبر التكامل مع مزوّد Git. نسخة داو لا تبتعد عن المستودع أبدًا بصمت.

## 11. التحقق

`dhow lint` (الـ CLI)، والمحرر، والسيرفر، كلها تستخدم مدقق Go نفسه. يفحص الـ YAML، والمخطط، والـ DAG، والـ matrix، وأخطاء الأنواع في CEL، والإضافات غير المثبّتة، ومخالفات السياسة. طريقة تثبيت `dhow lint` واستخدامه في [أداة سطر الأوامر `dhow`](cli.md).

- لكل مشكلة كود ثابت (`UPPER_SNAKE`، مثل `DAG_CYCLE` أو `RUN_EXPRESSION_NOT_ALLOWED`)، ومسار (`jobs.build.steps[2].run`)، وسطر، وعمود. الرسالة لا تكرر القيمة نفسها أبدًا، لأن أحدًا قد يلصق سرًا بالخطأ.
- `error` يمنع التشغيل، و`warning` (مثل صورة بالـ tag فقط) يظهر في نتيجة الـ lint وفي الواجهة.
- المفاتيح غير المعروفة، والمفاتيح المكررة، والـ anchors، والـ aliases، ومفاتيح الدمج، والـ tags الخاصة، كلها أخطاء.

## 12. التنفيذات

التنفيذ هو مرور واحد لخطوات النشر على commit واحد. السيرفر ينشئه من حدث، ويقرأ الملف في ذلك الـ commit، ويحوّل كل job في الملف (بعد الـ matrix) إلى تشغيل على جهاز تشغيل.

### 12.1 ما الذي يبدأ التنفيذ

- **`push` و`tag`:** رابط الإشعارات (webhook). كل commit يُنفَّذ مرة واحدة لكل ref: إذا وصل نفس الـ commit مرة أخرى لنفس الـ ref فلا ننشئ تنفيذًا جديدًا، حتى بعد حذف سجل الإشعارات (نحتفظ به 30 يومًا). والإشعارات تبدأ 600 تنفيذ بالأكثر لكل مشروع في الساعة، وهذا أكثر بكثير من مستودع مزدحم. وبعد ذلك يرد الإشعار بـ `429` مع `Retry-After`، ولا نسجّل شيئًا، ويستطيع المزوّد إرساله مرة أخرى لاحقًا.
- **`pull_request`:** إشعار من GitHub أو GitLab (M4.5 وM4.6). التنفيذ يستخدم آخر commit في الطلب، وليس commit دمج، لكي تظهر النتيجة على الـ commit الذي رفعته.
- **`manual`:** شخص عنده `run.trigger` على المشروع، عبر `POST /organizations/{id}/projects/{projectId}/runs` مع `Ref`، و`Sha` اختياري، و`Inputs`.
- **`api`:** نفس الطلب بمفتاح API فيه الصلاحية `run.trigger`.
- **أي commit يستخدمه التنفيذ اليدوي:** فقط commit وصل عبر الإشعارات لهذا الـ ref من المستودع نفسه، وليس من fork. نرفض الـ `Sha` الذي لم يصل بهذه الطريقة (`SHA_NOT_ON_REF`). وبدون `Sha` يستخدم التنفيذ آخر commit من هذا النوع في الـ ref، أو نرفض الطلب (`REF_HEAD_UNKNOWN`) حتى يصل أول push. الشخص الواحد يبدأ 60 تنفيذًا بالأكثر، والمشروع الواحد 240، في كل عشر دقائق.
- يكمل التنفيذ فقط إذا كان حدثه موجودًا في `on:` وتطابقت الفلاتر. وإلا ينتهي `skipped` بالسبب `TRIGGER_NOT_ENABLED`.
- الـ commit الذي ليس فيه الملف يعطي تنفيذًا `skipped` بالسبب `DEFINITION_NOT_FOUND`، ولا نرسل نتيجة للمزوّد.
- فلاتر `paths` تعمل عندما يرسل المزوّد الملفات التي تغيّرت (M4.5 وM4.6). قبل ذلك تطابق كل push.

### 12.2 مراحل التنفيذ

| الحالة | المعنى |
|---|---|
| `awaiting_approval` | طلب دمج من fork ينتظر موافقة مسؤول مشاريع (القسم 12.4) |
| `pending` | السيرفر يقرأ الملف في الـ commit ويتحقق منه ويثبّت صوره (القسم 12.5) |
| `queued` | تنفيذ أقدم من نفس مجموعة التزامن ما زال يعمل (القسم 12.3) |
| `running` | التشغيلات تعمل بترتيب `needs` |
| `succeeded`، `failed`، `canceled`، `skipped` | انتهى التنفيذ |

- الملف الخطأ ينهي التنفيذ `failed` بالسبب `PIPELINE_INVALID`. و`GET /organizations/{id}/projects/{projectId}/runs/{runId}` يعرض كل مشكلة بكودها وسطرها وعمودها، مثل `dhow lint` تمامًا.
- يبدأ الـ job عندما ينجح كل job في `needs` الخاصة به، أو يُتخطّى بسبب `if` الخاص به. وإذا فشل أحدها أو أُلغي، تصبح الـ jobs التي بعده `skipped` بالسبب `NEEDS_FAILED`.
- `cancel` يلغي فورًا التشغيلات التي تنتظر، والتشغيل الذي يعمل يتوقف عند النبضة التالية لجهاز التشغيل.
- `rerun-failed` يعيد التشغيلات التي فشلت أو أُلغيت، والتي تُخطّيت بسببها، بنفس الملف ونفس digests الصور. والتشغيلات التي نجحت تبقى كما هي.
- إذا لم يتمكن السيرفر من إنشاء تشغيلات تنفيذ ما، ينتهي التنفيذ `failed` بالسبب `RUN_EXPANSION_FAILED`، وتستمر تنفيذات كل المشاريع الأخرى.
- سجل كل تشغيل في `/organizations/{id}/jobs/{jobId}`. والدور على المشروع يُطبَّق هناك أيضًا: مسؤول المشاريع الذي خُفّض دوره إلى مشاهد في مشروع لا يستطيع إلغاء تشغيلات هذا المشروع من ذلك المسار.

### 12.3 التزامن

- `concurrency.group` يحدد مجموعة داخل المشروع. يعمل تنفيذ واحد فقط من كل مجموعة في نفس الوقت، والأحدث ينتظر `queued` بالترتيب.
- مع `cancel_in_progress: true` يلغي التنفيذ الجديد التنفيذات الأقدم في مجموعته **على نفس الـ ref** بدل أن ينتظرها. أما تنفيذات الـ refs الأخرى في المجموعة فلا تُلغى أبدًا، وينتظرها التنفيذ الجديد `queued`.

```yaml
version: 1
on:
  push:
    branches: [main, "release/*"]
concurrency:
  group: ${{ "deploy-" + git.branch }}
  cancel_in_progress: true
jobs:
  deploy:
    image: alpine:3.22@sha256:61bb7a95b0f3650f3039c0fcabe07674458cf0d13afa51aade6188bab8215b07
    steps:
      - run: ./deploy.sh
```

### 12.4 طلبات الدمج من fork

- التنفيذ يقرأ الملف من الـ commit الأساسي (base)، وليس من الـ fork أبدًا، فلا يستطيع طلب الدمج أن يضيف jobs أو يفتح اتصالات أو يغيّر الصور.
- نسحب آخر commit من الـ fork كبيانات فقط، ولا نقرأ منه أي إعداد.
- افتراضيًا ينتظر التنفيذ حتى يوافق مسؤول مشاريع أو أعلى (`POST .../runs/{runId}/approve`). والمسؤول (Admin) يستطيع أن يجعل سياسة الـ forks في المشروع `automatic`.
- الـ job الذي فيه `environment:` يُتخطّى (`FORK_PR_NO_ENVIRONMENT`)، والذي يطلب سرًا يفشل (`FORK_PR_NO_SECRETS`)، ولا يأخذ متغيّرات ولا حسابات سجلات صور.
- الذاكرة المؤقتة: افتراضيًا لا يقرأ التنفيذ منها شيئًا. والمدير (Admin) يستطيع أن يجعل `ForkCacheRestore` في المشروع `default_branch`، فيقرأ التنفيذ الذاكرة المؤقتة للفرع الافتراضي فقط، ما عدا ما كتبه تشغيل وصله سر. ولا يكتب فيها أبدًا.

### 12.5 الصور المكتوبة بالـ tag

- عند بداية التنفيذ يسأل السيرفر سجل الصور عن الـ digest لكل `image:` مكتوبة بالـ tag. بعدها كل تشغيل وكل إعادة في هذا التنفيذ تسحب `name:tag@sha256:…`، حتى لو تغيّر الـ tag لاحقًا. والتنفيذ يعرض هذه القيم في `ImagePins`.
- يصل السيرفر إلى سجل الصور عبر نفس الحماية المستخدمة مع Git: لا loopback، ولا link-local، ولا عناوين metadata، ولا عناوين خاصة إلا إذا سمح `DHOW_GIT_ALLOW_PRIVATE_CIDRS` بنطاقها. وينتظر 15 ثانية بالأكثر لكل صورة و30 ثانية للتنفيذ كله، ويسأل عن أربع صور في نفس الوقت وعن كل صورة مرة واحدة، ولا يتبع التحويلات (redirects)، ويقرأ 4 MiB بالأكثر.
- عنوان مفتاح السحب الذي يرسله سجل الصور يجب أن يكون `https` على نفس عنوان سجل الصور، أو على `auth.docker.io` أو `ghcr.io`، وعلى المنفذ 443 (أو منفذ سجل الصور نفسه). والنطاقات الخاصة في `DHOW_GIT_ALLOW_PRIVATE_CIDRS` لا تنطبق عليه أبدًا.
- مفاتيح السحب المجهولة (مثل Docker Hub) تعمل. وسجل الصور الذي يحتاج كلمة سر يعمل إذا أضفت حسابه في المشروع أو المؤسسة ([الأسرار والمتغيّرات](guides/secrets.md)). يستخدمه السيرفر هنا، ويرسله جهاز التشغيل عند سحب الصورة في ملف مؤقت خارج البيئة المعزولة يحذفه بعد السحب، فلا يراه التشغيل أبدًا. وجهاز التشغيل الذي لا يعلن `registry_auth` لا يأخذ هذا التشغيل. وتنفيذات طلبات الدمج (من المستودع نفسه أو من fork) لا تستخدم أي حساب.
- الـ tag الذي لا يعرفه سجل الصور يُفشل التنفيذ بالسبب `IMAGE_PIN_FAILED` عند `jobs.<id>.image`.
- `dhow lint` ما زال يحذّر من الـ tag (`IMAGE_NOT_PINNED`)، لأن كتابة الـ digest في الملف هي الأفضل دائمًا.

### 12.6 مستودعات Git العامة

- Gitea وForgejo وسيرفرات Git العادية ليس لها API للملفات، لذلك يسحب job صغير على جهاز تشغيل الـ commit ويقرأ الملف (job الاكتشاف، واسمه `dhow.discovery` في تشغيلات التنفيذ). ولطلب دمج من fork يسحب الـ commit الأساسي (base).
- يذهب فقط إلى جهاز تشغيل عنده ميزة `checkout`، مثل كل تشغيل فيه سحب. وحتى يتصل جهاز مثل هذا ينتظر في الطابور، وبعد مهلة الطابور يفشل وينتهي التنفيذ `failed` بالسبب `DISCOVERY_FAILED`.
- إذا لم يكن الـ commit في تاريخ الـ ref الخاص به، ينتهي التنفيذ `failed` بالسبب `SHA_NOT_ON_REF` قبل أن يعمل أي تشغيل من تشغيلاتك.
- لا نثق في جهاز التشغيل بشأن الملف. يطبع التشغيل في سجله كائنات Git الخام التي على مسار الملف (الـ commit، وكل مجلد على المسار، والملف)، ويحسب السيرفر الـ hash لكل منها بصيغة كائنات الـ commit (SHA-1 أو SHA-256)، ويتتبع السلسلة من رقم commit التنفيذ حتى ملف عادي. ولا نقرأ إلا ملفًا ثبت بهذه الطريقة. والملف أو المجلد المزوّر، أو commit غير commit التنفيذ، أو الرابط الرمزي، أو commit أو مجلد أكبر من 1 MiB، أو ملف أكبر من 256 KiB، كلها تنهي التنفيذ `failed` بالسبب `DEFINITION_UNVERIFIED`.
- الملف غير الموجود، أو الرابط الرمزي أو المجلد أو الـ submodule في مكانه، يعطي تنفيذًا `skipped` بالسبب `DEFINITION_NOT_FOUND`، ويجب أن تثبت الكائنات ذلك أيضًا. والتشغيل الذي لا يذكر `true` أو `false` في `dhow_found` ينهي التنفيذ `failed` بالسبب `DISCOVERY_FAILED`.
- بعدها يسحب كل تشغيل في التنفيذ commit التنفيذ بمفتاح المستودع (deploy key) عبر SSH، ولا نقبل إلا مفتاح الخادم الذي أكّده المدير، أو بدون بيانات دخول عبر HTTPS.
- السيرفر المبني بدون صورة السحب ينهي هذه التنفيذات `failed` بالسبب `CHECKOUT_UNAVAILABLE`.
